# 可靠性：这个工具将来会遇到什么

> 2026-11-14　配套代码：`src/lib/*`、`prisma/migrations/`、`.github/workflows/ci.yml`

这份文档回答一个问题：**如果这个系统真的被一个团队用上半年，会在哪里坏掉。**

下面按"已经补上的"和"还没补、需要知道"两部分写。凡是没做的，都写清楚为什么现在不做。

---

## 一、这一轮补上的

### 1. 版本化数据库迁移

原来改表结构用的是 `prisma db push`，它直接把库改成和 schema 一致，没有版本记录，也没法回滚。生产上这是不可接受的。

现在有 `prisma/migrations/20261114000000_init/`，已经对现有开发库做了基线（`migrate resolve --applied`）。之后的变更流程：

```bash
pnpm exec prisma migrate dev --name 描述    # 本地开发，生成并应用迁移
pnpm db:deploy                              # 部署环境，只应用不生成
pnpm exec prisma migrate status             # 检查是否落后
```

**为什么重要**：迁移文件进版本库之后，任何一台机器拉到代码就能还原出结构一致的数据库；出问题时也能看到每一步改了什么。

### 2. 租约接受的并发竞态

两个连接器可能同时接受同一个租约。原实现是先读状态、再更新，中间有窗口；两个请求都可能读到"待领取"，各自建一个会话。

现在改成条件更新抢占：

```ts
const claimed = await tx.taskLease.updateMany({
  where: { id, status: "OFFERED" },
  data: { status: "ACTIVE", ... },
});
if (claimed.count === 0) throw new LeaseRaceError();
```

抢不到的直接返回 409，事务回滚，不会留下第二个会话。

**实测**：同一租约并发发起两次接受，结果 1 个 200、1 个 409，数据库里只有 1 条会话。

### 3. 任务状态流转的并发覆盖

两个人同时把同一个任务推到不同状态时，后提交的一方会覆盖前一方。

现在流转时带上读取到的版本号：

```ts
const applied = await tx.task.updateMany({
  where: { id: task.id, version: task.version },
  data: { status, version: { increment: 1 }, ... },
});
if (applied.count === 0) throw new Error("任务已被他人修改，请刷新后重试（版本冲突）");
```

整个事务回滚，事件、消息、验收记录都不会留下半截。

### 4. 写接口限流

配对、派发、接受租约三类接口加了频次限制（60 秒窗口）。超限返回 429 和重试间隔。

局限写在代码里：限流是**进程内计数**，多实例部署时额度会乘以实例数。单实例够用，扩容时要换成 Redis。

### 5. 健康检查

`GET /api/health` 返回数据库连通性、版本、运行时长与查询延迟。数据库不通时返回 503，反向代理或监控可以直接据此摘流量。

### 6. 错误兜底

- `app/error.tsx`：任何页面抛错都显示一个可读的错误页，带重试与"回到项目大厅"，不白屏。
- `app/not-found.tsx`：404 说明可能的原因（链接失效、项目归档、无权限）。

### 7. 事件保留策略

事件表只增不减，半年后会成为最大的表。新增 `scripts/prune-events.ts`：

```bash
pnpm db:prune                 # 预演，只统计不删
pnpm db:prune --days=30 --apply   # 真删
```

只清理 `message.posted` 与 `agent.progress` 两类过程事件；决策、产物、验收、任务状态变更、会话起止一律不动。

### 8. 连接器可以发布了

`connector/package.json` 补了 `files`、`keywords`、`author`，加了 MIT LICENSE，去掉了 `private`。`npm pack --dry-run` 打出 13 个文件、17.2 kB 的包，`bin` 指向 `coflow`。

**还没发**：发布需要 npm 账号与一次性验证码，这一步得你自己来。命令是 `cd connector && npm publish`。

### 9. 持续集成

`.github/workflows/ci.yml`：安装依赖、生成 Prisma 客户端、类型检查、ESLint、8 套单元测试、生产构建。

构建时用一个假的 `DATABASE_URL`，已验证可以脱离数据库完成构建（所有页面都是动态渲染）。

## 二、将来会遇到、但现在还没解决的问题

按发生概率从高到低排。

### A. 数据量增长（3—6 个月后）

**会发生什么**：事件表到十万条量级后，时间线页、周报页开始变慢；上下文快照占空间最大（每次派发一份完整 JSON）。

**现在状态**：时间线只取最近 120 条，周报按 7 天窗口查询，暂时不会出事。快照没有任何清理。

**已做**：`scripts/prune-events.ts` 现在同时清理事件与快照。快照删除前会排除仍被租约或会话引用的，避免追溯断链。

**剩余建议**（按优先级）：
1. 给 `context_snapshots` 加**按任务**的保留上限（如每个任务最多 20 份），当前只按时间；
2. 事件表按 `project_id + occurred_at` 加索引（目前已有 `[projectId, occurredAt]`，够用）；
3. 真到百万级再考虑分区表，现在做是过度设计。

### B. 长轮询占用连接（接入第三个设备后）

**会发生什么**：`/api/leases/pending?wait=25` 每次挂起 25 秒。三个连接器同时在线就是三条常驻连接，几十个设备时可能打满反向代理的连接数。

**现在状态**：单机自用没问题。

**建议动作**：连接数超过二十时改成 WebSocket 或 SSE；在那之前不用动。

### C. 多人同时编辑同一任务（每天都在发生）

**现在状态**：已用版本号挡住覆盖，后改的人会收到"已被他人修改"。

**还缺**：界面上没有"正在被谁编辑"的提示，用户会反复撞冲突。

**建议动作**：先统计冲突频率；如果一天超过几次，再考虑加编辑锁或实时协作。

### D. 会话与凭据（安全）

**已经做的**：会话存哈希、设备令牌存哈希、撤销即时生效、验证码限次。

**还缺**：
- 没有会话列表与"退出所有设备"；
- 没有登录失败锁定；
- 生产环境没有二次验证。

**建议动作**：上线前补"会话列表 + 单条撤销"，成本很低。

### E. 备份与恢复（上线前必须有）

**现在状态**：没有任何备份机制。

**建议动作**：至少每天一次 `pg_dump`，保留 7 份；恢复流程写进运维文档并演练一次。这一步不做，数据库坏一次就全没了。

### F. 升级流程（版本发布时）

**现在状态**：没有版本号策略，没有回滚方案。

**建议动作**：
1. 发布遵循 `迁移 → 部署代码 → 冒烟测试` 的顺序，迁移只向前兼容；
2. 每次发布前打 tag，数据库迁移文件与代码同一个 commit；
3. 冒烟清单：`/api/health` 200、登录成功、能建任务、能派发一次。

### G. 跨平台

**现在状态**：只在 Windows 11 上验证过。连接器对 `.cmd` / `.ps1` 做了处理，路径统一走 `path` 模块，理论上 Linux/macOS 可用，但没实测。

**建议动作**：第一次部署到 Linux 时，重点测三件事——工具探测（`which` vs `where`）、子进程调用、路径大小写。

### H. 产品本身还没有被验证

**这是最大的一条。** 上面都是工程问题，这一条是产品问题：没有任何真实团队用它跑过完整项目，所以"能不能减少返工"没有证据。

工程上再稳，也可能是在打磨一个没人需要的工具。

## 四、有意不做的事

| 事项 | 为什么不做 |
| --- | --- |
| 分布式锁、多实例部署 | 当前只有单团队使用，单实例足够；做了也没有场景验证 |
| 事件表分区 | 十万级之前没有收益 |
| 实时协同编辑 | 冲突提示已经够用，先看真实冲突频率 |
| 阶段五（自托管、组织权限、适配器市场） | 文档里写明要由真实负载推动，现在做是空转 |
| 向量检索 | 上下文包目前靠确定性规则裁剪，效果可解释；加语义召回会让"为什么没给这条"变得说不清 |
