# CoFlow 页面功能说明书 · 给 Figma AI 的完整提示词（纯功能版）

> 用法：整段复制给 Figma AI。视觉风格、布局结构、配色、字体、组件形态全部由它决定；本文件只规定「每页有哪些内容、能做什么、有哪些状态」。
> 若一次生成不完 14 页，按「页面清单」分批喂，但「产品背景」「角色与权限」「任务状态机」每次都要带上。

---

## 提示词正文

你是一位资深产品设计师。请为一款名为 **CoFlow** 的 B 端协作工具设计完整的高保真界面与组件库。

**视觉风格、布局方式、配色、字体、图标、动效，全部由你决定**——我们只提供产品的功能与内容，创意留给你。
唯一的要求是：这是一个给专业小团队每天使用的工具，信息密度高、内容多、状态复杂。设计要能承载这些内容，而不是把它们简化掉。

界面语言：**简体中文**。主要平台：**Windows 桌面端 1440×900**。

## 一、产品背景（理解它是干什么的，才能决定信息如何组织）

CoFlow 是「多人 + 多 AI Agent」的项目协作工作台。

团队在这里写项目章程、拆任务、讨论、提交产物、做验收。成员各自电脑上的 AI 工具（比如 Claude Code）通过本地连接器接入平台，领取任务、拿上下文、交结果。

它和普通协作工具的根本区别：**它管理的是"事实"，不是"消息"**。
- 聊天只是过程，不代表进度
- 只有「被确认的决策」「带证据的产物」「人工给出的验收结论」才进入项目事实
- AI 不能自己把任务标成"已完成"，只能提交到"待验收"

所以界面上经常需要同时呈现三类信息：**过程（讨论/事件）**、**当前事实（任务/产物/验收）**、**风险与待办**。这三者的视觉层级如何区分，是你最重要的设计课题。

## 二、用户角色（决定界面差异）

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 发起人 | 改目标、改成员角色、最终验收 | — |
| 负责人 | 拆任务、派发、改项目阶段、验收 | 改成员角色 |
| 成员 | 建任务、发言、提交产物 | 下验收结论、退回 |
| 评审 | 做验收结论、退回 | 改项目目标 |
| 观察员 | 只看 | 任何写入（界面上相关按钮应消失，而不是变灰） |

**重要**：角色不同，同一页面上的可用操作不同。设计时请体现这一点。

## 三、关键概念（界面上的名词）

- **项目章程**：目标、目标用户、交付范围、非目标、硬性约束、验收标准。有版本号，修改会生成新版本。
- **任务状态机**：待澄清 → 待认领 → 已就绪 → 进行中 → 待验收 → 已完成；另有旁路状态：已阻塞、已暂停、已取消。
- **决策**：讨论中形成的结论，必须被"确认"才生效。状态：提案 / 已确认 / 已被替代。
- **产物**：代码提交、构建包、文档、设计稿、图片、数据表、测试报告、外部链接、说明。
- **上下文包**：Agent 开工前拿到的一份按任务裁剪的资料，有四层（章程 / 任务 / 决策与阻塞 / 工作区），带哈希与 token 预算。
- **Agent 端点**：某个成员电脑上的一个工具实例，有能力等级：自动接入 / 半自动 / 手动。
- **租约 / 会话**：一次执行授权与执行过程，有时效、可撤销。

## 四、页面清单（共 14 页）

每页请覆盖：**目的、包含内容、可执行操作、页面状态**。文案是真实的，请直接使用。

### 1. 登录

**目的**：用邮箱验证码登录。

**内容**：品牌名 CoFlow 与一句定位；邮箱输入；验证码输入（6 位）；说明文字「用邮箱验证码登录。项目数据属于你的账号，不属于某台电脑。」；底部提示「继续即表示同意：平台只保存项目事实，不读取、不保存你本地工具的模型密钥。」；一个次要入口「了解事件协议」。

**操作**：发送验证码 → 输入验证码 → 登录；切换邮箱。

**状态**：发送中；60 秒冷却倒计时；验证码错误；验证码已过期；开发环境下的"快速进入"身份列表（仅在本地开发出现）。

---

### 2. 项目大厅（首页）

**目的**：一眼看到所有项目的状态，进入某个项目。

**内容**
- 页面标题与一句说明「同一份事实，给人看，也给 Agent 读。」
- 四个统计数字：项目总数、进行中任务数、待验收数、阻塞数
- 项目卡片列表，每张卡片包含：项目代号（如 ZX）、项目阶段（定义/开发/联调/验收/归档）、项目名称、目标摘要（两行）、交付进度百分比与进度条、状态计数（进行中 / 待验收 / 阻塞）、成员头像、最近活动时间
- 一张「新建项目」的入口卡
- 页面底部一段产品说明：标题「聊天负责交流意图，任务与产物负责表达事实」，配四个要点（目标 / 任务 / 决策 / 产物）

**操作**：进入项目；新建项目。

**状态**：没有任何项目时的空状态（引导去创建第一个项目）；未完成上手流程时顶部出现一条引导条「15 分钟跑通第一个闭环」。

---

### 3. 新建项目（分步向导，5 步）

**目的**：把一个想法变成结构化的项目章程和第一批任务。

**第 1 步 · 基本信息**
- 模板选择：空白项目、软件小团队（6 个任务）、内容创作（6 个任务）、竞赛项目（6 个任务）。每张模板卡显示名称、一句描述、任务数量。
- 项目名称、项目代号（2–6 位大写字母或数字）、一句话说明

**第 2 步 · 目标与范围**
- 项目目标、目标用户、交付范围、非目标、硬性约束（都是多行文本）

**第 3 步 · 验收标准**
- 验收标准（多行，逐条可检查）
- 若第 1 步选了模板：显示一条模板说明（会生成哪些里程碑和任务），替代"首个里程碑"输入；否则显示"首个里程碑"输入

**第 4 步 · 成员与角色**
- 发起人固定为当前用户
- 可勾选的成员列表（头像、姓名、账号），勾选后可为其选择角色：负责人 / 成员 / 评审 / 观察员
- 一句权限说明

**第 5 步 · Agent 接入**
- 说明零密钥接入：工具授权归原工具，项目授权归 CoFlow
- 「本次创建将写入」清单：项目、章程、成员、模板、事件
- 创建按钮

**状态**：当前步骤未填完时"下一步"不可点；创建中；创建失败显示原因；已完成步骤显示勾选标记。

---

### 4. 项目工作台（核心页面）

**目的**：项目的日常中枢——看方向、看讨论、看要处理的事。

**左区 · 方向**
- 项目章程（当前版本号）：项目目标、交付范围、非目标、硬性约束、验收口径
- 里程碑列表：名称、进度百分比、任务数、状态
- 成员列表：头像、姓名、角色

**中区 · 讨论**
- 频道名（如 #general）与成员头像组
- 消息流，消息类型必须可区分：
  - 普通讨论：头像、姓名、时间、正文
  - 系统事件：创建项目、升级章程、验收退回等（与聊天明显不同）
  - 决策提案：带「决策提案」标记
  - 产物提交：带「产物」标记与位置
  - 阻塞求助：带「阻塞」标记
  - Agent 汇报：应弱化或折叠，不能和人的发言混在一起
- 输入框，支持 Ctrl/⌘ + Enter 发送

**右区 · 要处理的事（信息密度最高的区域）**
按优先级依次包含：
1. **风险**：按高/中/低分级，每条显示任务名与原因（如"已逾期 3 天""阻塞 5 天，等待：营业执照""等待验收 6 天"），以及高/中的数量汇总
2. **需要处理**：待确认的决策（含确认按钮，仅发起人/负责人可见）、待验收任务、阻塞任务（含所需支持）
3. **正在执行**：当前有哪些 Agent 会话在跑，显示工具类型、所属任务、声明的路径
4. **已确认决策**：标题、决策人、时间
5. **最新产物**：类型、名称、版本
6. **Agent 端点**：可用端点数量、执行中的会话数，或"还没有绑定端点"的引导
7. 最后同步时间

**操作**：发消息；对消息「形成决策」（填写标题、结论、理由、影响范围后提交提案）；确认决策；点击任务卡片跳转。

**状态**：观察员只读（输入框不可用，确认按钮消失）；没有消息的空状态；没有风险时不显示风险区。

### 5. 任务看板

**目的**：按状态看所有任务，做分工。

**内容**
- 页面说明一句话：状态由规则驱动，不能跳级
- 六个状态列：待澄清、待认领、已就绪、进行中、待验收、已完成。列头显示状态名与任务数量，列底显示权重合计。
- 任务卡：优先级（P0–P3）、返工轮次标记、截止日期、任务标题、负责人头像、产物数、依赖数、权重
- 「旁路状态」区域：已阻塞 / 已暂停 / 已取消的任务单独列出，阻塞任务显示原因
- 新建任务按钮

**操作**：进入任务详情；新建任务（弹窗，字段见下）。

**新建任务弹窗字段**：任务名称、负责人、优先级、权重、里程碑、截止日期、任务说明、输入材料、工作范围、非工作范围、验收标准。

**状态**：没有任务的空状态；列内为空的提示文字。

---

### 6. 任务详情

**目的**：一个任务的完整事实与所有操作。

**主区**
- 任务标题、状态、优先级、所属里程碑、返工轮次
- 元信息：负责人、验收人、截止日期、权重
- 任务定义：说明、输入材料、工作范围、非工作范围、验收标准（验收标准应突出）
- 编辑任务定义（保存后版本号 +1，可能发生冲突："任务已被他人修改，请刷新后重试"）
- 产物与证据列表：类型、名称、位置、版本、提交人、时间
- 验收记录：结论（通过/退回/补充材料）、评审人、逐条结论、意见、时间

**侧区**
- 状态机面板：当前状态、变更说明输入、当前可执行的动作按钮
  - 从"待澄清"可到"待认领"（需已填输入与验收标准）
  - 从"待认领"可到"已就绪"（需已指定负责人）
  - 从"已就绪"可到"进行中"
  - 从"进行中"可到"待验收"（需至少一项产物，或填写无产物说明）
  - 从"待验收"可到"已完成"或退回"进行中"（**只有验收权的人能操作**）
  - 任意状态可"标记阻塞"（必须填写原因与所需支持）或"取消"
  - 已完成可"重新打开"（生成新的返工轮次）
- 验收结论表单：通过 / 补充材料 / 退回 三选一 + 逐条对照结论 + 补充意见（仅待验收且当前用户有验收权时出现）
- 提交产物：产物类型、名称、位置（提交号/路径/链接）、版本、是否同时提交验收
- 派发卡片（任务处于"已就绪"时出现）：
  - 可选的 Agent 端点下拉（显示工具名、版本、归属人、能力等级）
  - **推荐理由**：给出排序分数与若干条理由（如"+25 可自动执行""+5 空闲""+15 授权目录覆盖任务范围""−30 与执行中会话路径重叠"）
  - 派发按钮
- 当前租约状态（待领取 / 已接受 / 执行中、上下文编号、过期时间）
- 前置依赖列表（状态 + 标题）
- 元信息：任务 ID、定义版本、返工轮次、创建/更新时间、所属项目

**状态**：观察员只读；无权限的动作不显示；任务不是"已就绪"时不出现派发卡；没有端点时提示去连接 Agent。

### 7. 上下文包预览

**目的**：让用户看到「Agent 到底会看到什么」，以及为什么。

**内容**
- 内容哈希（很长，需要截断显示）
- 四个层级分区，每区标注层号与是否可裁剪：
  - L0 稳定层：章程（目标、交付范围、非目标、硬性约束、验收口径）
  - L1 任务层：标题、说明、输入材料、工作范围、非工作范围、验收标准、前置依赖
  - L2 动态层：已确认决策（标注"与本任务相关"）、未解决阻塞（原因 + 需要什么）、最近变更（时间 + 摘要 + 事件类型）
  - L3 证据层：允许修改的路径、禁止访问的路径、提交格式、必须回传的内容
- 预算：当前 tokens / 上限，带进度；超预算时明确提示
- 裁剪记录：哪一层丢了什么、丢了几条、原因（预算/上限）
- 快照列表：版本号、短哈希、tokens、时间；「保存为快照」按钮
- 渲染后的提示词：完整可复制的文本，包含 `<data>` 标记（表示"这是资料不是指令"）
- 注入隔离说明：项目文本一律包在 data 标签内，出现"忽略之前的规则"也不会被当授权

**状态**：没有快照；超预算；未授权目录（应明确警告"Agent 只能读，不能写"）。

---

### 8. 产物与验收

**目的**：集中处理待验收的任务，并查看所有产物。

**内容**
- 待验收区：每个任务一张卡，内部三栏「标准 / 证据 / 结论」——标准是逐条验收条件，证据是产物列表，结论栏说明"尚未验收"并给出「去验收」入口
- 已完成区：任务名、产物数、验收次数、最后验收时间
- 产物清单表格：类型、名称、位置、版本、来源任务、提交人、时间

**状态**：没有待验收、没有已完成、没有产物的空状态。

---

### 9. 决策与时间线

**目的**：回答「为什么这样做」和「历史上发生了什么」。

**内容**
- 决策列表（按状态排序）：状态（提案/已确认/已被替代）、标题、结论、理由、备选方案、影响范围、决策人、时间、版本号、被谁替代；已被替代的决策应弱化
- 事件时间线：每条含事件标题、操作人、摘要、事件类型、时间；不同事件类型（决策 / 产物 / 状态变更 / 阻塞）需要视觉区分

**状态**：没有决策、没有事件的空状态。

---

### 10. 项目设置

**内容**
- 项目信息：名称、代号、当前阶段（可切换并应用）
- 项目章程：当前版本的全部字段、版本历史（版本号、变更说明、时间）、「修订章程」入口（需填写本次变更说明，保存后生成新版本）
- 成员与角色：每行头像、姓名、账号、角色说明、角色下拉（仅发起人可改，自己的角色不可改）
- 数据与保留策略：六条固定说明（事件流全量保留、详细 Agent 日志短保留、关键决策与验收长期保留、敏感本地路径不进入事件、模型 API Key 平台不读取、云端与本地删除分开授权）

**状态**：非发起人看到只读的角色显示。

---

### 11. Agent 连接

**目的**：把成员电脑上的 AI 工具接进来，并管理它们的权限。

**内容**
- 「连接一台设备」区域：三步说明（在目标电脑执行命令 → 终端显示配对码 → 在页面输入）、配对码输入框（8 位，形如 ABCD-2345）、授权按钮
- 「两层授权」说明：工具授权归原工具（平台不碰登录与模型），项目授权归 CoFlow（能进哪个项目、读哪些任务、写哪些目录）
- 设备列表：设备名、系统、在线状态、配对时间、撤销按钮
  - 每台设备下有若干 Agent 端点，每个端点显示：工具名与版本、能力等级（自动接入 / 半自动 / 手动，必须视觉可区分）、能力说明、授权目录按钮、绑定项目、最后心跳时间
  - 半自动/手动端点要显示**降级原因**（例如"该版本不支持无头 JSON 输出"），并说明"不能自动执行，只能 pull + 人工"
  - 授权目录：可输入多个路径（逗号分隔）
- 已撤销设备区

**状态**：没有任何设备；配对码错误/过期/已使用；保存授权目录失败。

### 12. 周报（这一周发生了什么）

**目的**：用一周的真实数据判断这套流程值不值得用。

**内容**
- 标题与日期区间
- 叙述区：4–6 条由数字生成的事实句（如"本周在 1 个项目里新建 5 个任务、完成 2 个""验收 2 次，全部通过""从建任务到通过验收，周期中位数 3.7 天""上下文包平均 869 tokens"）
- 五个指标：完成数、新建数、通过率、Agent 会话数（含失败数）、平均上下文 tokens
- 两张七日图表：每天新建的任务数、每天通过验收的任务数（同一种度量，按天）
- 按项目表格：项目、新建、完成、退回、完成率
- 「卡住的地方」：阻塞任务与所需支持
- 「Agent 失败原因」：按原因聚合（超时 / 越界修改 / 输出无法解析 / Agent 报错）
- 顶部入口「15 分钟上手」

**状态**：这一周完全没有活动时的空状态（说明"要么还没开始，要么事情停在了别处"）。

### 13. 上手（15 分钟跑通第一个闭环）

**目的**：让新用户五步跑通一次完整交付。

**内容**
- 标题、说明、进度（已完成步数 / 5）、进度条
- 五个步骤卡，每步包含：序号（完成显示勾选）、标题、预计时长、说明、「为什么需要这一步」、命令行（可复制）、动作按钮
  1. 建一个项目
  2. 连接一台设备（命令：npx coflow-connector login）
  3. 给端点授权目录
  4. 有一个「已就绪」的任务
  5. 跑通一次完整交付（命令：coflow pull 或 coflow run）
- 完成状态：全部完成时显示一条完成提示与「看这一周发生了什么」入口
- 未完成时：顶部一条「下一步 · 约 X 分钟 · 去…」的引导
- 底部「如果卡住了」：三条排查提示

**注意**：每一步的完成状态来自真实数据，不是用户自己勾的。设计上要体现"这是系统判定"。

### 14. 事件协议（说明页）

**目的**：给开发者和第三方看的协议文档。

**内容**：原则（四条）、事件公共字段表（13 个字段）、事件类型清单、一段示例 JSON、上下文包分层表（L0–L3）、Agent 回传合同（7 条）、已实现与设计不一致的地方（偏差表）。

这是一个偏阅读型的页面，信息以文字和表格为主。

## 五、全局元素

**顶部导航**：品牌标识与产品定位、四个入口（项目大厅 / Agent 连接 / 本周 / 事件协议）、当前用户身份、退出登录。开发环境额外有一个身份切换控件。

**项目内导航**：项目代号、阶段、项目名、交付进度、五个入口（工作台 / 任务与分工 / 产物与验收 / 决策与时间线 / 项目设置），部分入口带数量角标。

**每个页面都要考虑的通用状态**
- 空：没有项目 / 任务 / 产物 / 决策 / 活动
- 加载：骨架屏
- 错误：请求失败、权限不足、版本冲突
- 只读：观察员视角，操作入口消失并说明原因
- 断线：显示"最后同步时间"，不得伪装成实时

## 六、需要交付的内容

1. **14 个桌面页面**，1440×900：登录、项目大厅、新建项目、工作台、任务看板、任务详情、上下文包、产物与验收、决策与时间线、项目设置、Agent 连接、周报、上手、事件协议
2. **移动端 3 页**，390×844：工作台、任务看板、任务详情
3. **组件库**：把重复出现的元素抽成组件，至少包含——任务状态徽标（9 种）、优先级标签、角色标签、能力等级徽标、按钮（主要/次要/幽灵/危险）、输入框（单行/多行/下拉/复选）、卡片、表格、提示条（信息/警告/危险/成功）、空状态、头像与头像组、进度条
4. 以上所有组件需包含状态变体（默认/悬停/禁用/选中）

**设计要求**：视觉风格、布局、配色、字体、图标系统完全由你决定。唯一需要保证的是——信息不能被删减，状态必须能被区分，操作必须清楚。

## 补充说明（给使用者，不用粘给 Figma）

- 如果一次生成不完，先做**工作台**和**组件库**，这两块定调；其余页面基于组件库扩展。分批时把「产品背景」「用户角色」「关键概念」每次带上。
- 生成后重点检查四件事：① 六种任务状态是否真的能一眼区分 ② 工作台右区（风险/待办/执行中）是否没有被简化掉 ③ 观察员视角下的按钮是否消失而不是变灰 ④ 信息密度是否被稀释成"每个字段一张大卡片"。
- Figma 想发挥创意时，最容易被牺牲的是"密度"和"状态区分"。这两条是产品的命脉，别让步。
